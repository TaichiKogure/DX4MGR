# Plan6 パラメータ設定・活用ガイド

本ドキュメントでは、Plan6シミュレーションを効果的に活用するためのパラメータスタディの方針、設定のコツ、および詳細な操作マニュアルを解説します。

---

## 1. パラメータスタディの進め方 (DOEの方針)

R&Dプロジェクトは不確実性が高く、単一のシミュレーション結果だけで判断するのは危険です。以下の手順で**実験計画法（DOE: Design of Experiments）**に基づいた分析を行うことを推奨します。

### ① ベースラインの確立
まずは現状（または標準的な想定）のパラメータで実行し、プロジェクトがどのように推移するかを確認します。
- KPI（Total Gain, 完了数）の確認
- ヒートマップでのボトルネック特定

### 1.1 感度分析の実施例 (DOE01, DOE02)
DOE（実験計画法）を用いることで、各パラメータの「感度」を定量的に把握できます。

- **DOE01 (リソースと周期)**: 
  - 結論: エンジニア数を増やすと、単位時間あたりの実験回数が増え、技術の成熟が早まりますが、DRコストも増大します。
  - 推奨: リソースが限られている場合は、DR周期を適切に（例: 2週間）設定し、リワークの早期発見を目指すのが「堅実」な戦略です。
- **DOE02 (技術的厳格さと減衰)**:
  - 結論: 知識減衰率が高い環境では、頻繁な実験を行っても成果が定着しにくいため、ドキュメント化やチーム間連携を強化するパラメータ調整が必要です。

### ③ トレードオフの探索
「人を増やせば早く終わるが、コストも増える」「DRを厳しくすれば品質は上がるが、リワークが増えて遅延する」といったトレードオフの関係を、シミュレーションを通じて定量化します。

## 2. 主要パラメータ解説と設定のコツ

### 2.1 リソース配分 (Resource Tab)
- **エンジニア数 (n_servers)**:
  - **コツ**: 工程間のバランスが重要です。Researchに人を割きすぎると、Prototypeで「仕事の渋滞（WIPの滞留）」が発生します。
  - **指標**: WIPヒートマップで色が濃くなっている工程の人数を増やすのが基本戦略です。
- **WIP制限 (WIP Limit)**:
  - **コツ**: 同時に抱える仕事量を制限することで、一つのジョブに対する集中度を高めます。制限が緩すぎると、多くの仕事が停滞し、リードタイムが伸びる原因になります。

### 2.2 技術閾値と動態 (Tech Tab)
- **DR不確実性/成熟度閾値**:
  - **コツ**: プロジェクト前半（DR1）は「不確実性を下げる」こと、後半（DR2/3）は「成熟度を上げる」ことに重点を置いた設定が現実的です。
  - **影響**: 閾値を厳しく（不確実性を低く、成熟度を高く）設定すると、やり直し（リワーク）が増えますが、最終的な製品品質（Gain）は向上します。
- **知識減衰率 (Decay)**:
  - **コツ**: 時間経過とともに失われるノウハウを表現します。長期間のプロジェクトでは、この値を高めに設定し、こまめなDRやドキュメント化（暗黙知度の低減）の効果を検証します。
- **暗黙知度 (Tacitness)**:
  - **コツ**: 技術が属人化している度合いです。これが高いと、チーム間の引き継ぎ（Res -> Protoなど）で情報が大きく劣化します。

### 2.3 通信とプロセス管理 (Comm Tab)
- **情報の欠落・歪み率**:
  - **コツ**: 部門間の壁を表現します。これを下げる施策（共通ツールの導入など）が、どれだけプロジェクト期間短縮に寄与するかをシミュレーションできます。
- **DR会議周期**:
  - **コツ**: 周期を短くすると早期に問題を発見できますが、会議コストが累積します。開発スピードとコストの最適バランスを探ります。

## 3. GUI操作マニュアル

### ステップ1：パラメータの設定
左側の設定パネルにある4つのタブを切り替えて設定を行います。
1. **プロジェクト**: 日数や戦略（Random/Strategic）を選択。
2. **リソース**: 各工程の人員と仕掛品制限を設定。
3. **技術・ゲート**: 合格基準やリワークの厳しさを設定。
4. **通信・DOE**: 部門間連携の質やDRの頻度を設定。

### ステップ2：実行
- **[Run Single Simulation]**: 現在の設定で1回実行します。中央のログに経過が表示されます。
- **[Run DOE Batch]**: 乱数シードを変えながら連続実行し、平均的な傾向を分析します。結果は `reports/batch_results.csv` に保存されます。

### ステップ3：結果の分析
右側の可視化エリアをスクロールして、以下のグラフを確認します。
- **KPI Summary**: 最終的な利得とコストの推移。
- **WIP Heatmap**: どの工程がボトルネックになっているか。
- **Tech Evolution**: 技術が目標値に向かって成長しているか。

### ステップ4：詳細レポートの出力
**[Output Detailed Report]** ボタンを押すと、`reports/viz/` フォルダに高解像度の分析画像が保存されます。プレゼン資料などへの引用に便利です。

## 4. 分析目的別の推奨パラメータ構成 (テンプレート)

| 分析のゴール | 極端な例 (Extreme) | 堅実な例 (Solid) | 設定のポイント |
| :--- | :--- | :--- | :--- |
| **開発リードタイム短縮** | 大量リソース + 高頻度DR | 5名程度 + 2週間DR | リソース飽和に注意 |
| **製品品質の極大化** | 厳格な閾値(0.1) + 高品質承認者 | 標準閾値(0.4) + Senior承認者 | リワーク率の監視 |
| **技術継承・暗黙知対策** | 高い減衰率 + 複雑なチーム連携 | 低い減衰率 + 密な通信 | 通信劣化率を調整 |

## 5. 成功のためのパラメータ設定のヒント

1. **ボトルネックを狙い撃つ**: 
   WIPヒートマップを見て、常に赤い（仕事が溜まっている）工程を見つけたら、そこに従事する人数を1人増やしてみましょう。
2. **「急がば回れ」の検証**: 
   DR1の周期をあえて短く（頻繁に開催）し、初期段階で不確実性を徹底的に叩く戦略が、最終的なリワークをどれだけ減らすかを確認してみてください。
3. **デジタルツインの活用**: 
   `use_digital_twin` をONにすると、`configs/past_logs.csv` に基づいた現実的な技術成長カーブが再現されます。まずはこれをONにして、現実との整合性を確認することをお勧めします。
